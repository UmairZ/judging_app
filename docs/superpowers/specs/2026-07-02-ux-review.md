# UX Review — Post-Phase-4 Pass

**Date:** 2026-07-02 · **Method:** hands-on walkthrough of every flow (organizer, judge, display, first-run) against the emulator, desktop 1440px + phone 390px, screenshots per screen. Functionality is solid throughout — this review is purely experience.

---

## P0 — Product identity (needs a decision from you)

### 1. The SaaS is still wearing your event's clothes
The browser tab says **"Ibn Katheer Qur'an Competition — Judging"** on the landing page, the sign-up page, and inside every stranger's competition. The Ibn Katheer logo sits in the admin sidebar, the leaderboard header, and the judge welcome screen. The favicon is your event's.

This is the single biggest blocker to putting real organizations on the product — an organizer from another masjid signs up and runs their contest inside someone else's brand.

**Fix path:** (a) pick a product name + simple wordmark (this is a naming decision only you can make); (b) sweep `index.html` title/favicon, `AdminApp` sidebar, `Leaderboard`/`Projector` headers, `WelcomeScreen`, and the seed's demo copy; (c) later roadmap item: per-organization logo upload so each tenant's screens show *their* brand (projector especially — that's on stage).

---

## P1 — Highest-impact experience gaps

### 2. The judge grading screen is unusable on phones
At 390px the three-column desktop layout collapses: header text overlaps, the score-breakdown column is clipped mid-word, and the center column — the actual deduction steppers, the whole point of the screen — is squeezed to a sliver behind a horizontal scrollbar.

This matters more than anything else on this list because **join codes explicitly invite judges onto their own phones** — the product's headline flow sends users to its worst screen. The responsive pass is already roadmap item #2a; this review says: make it the very next engineering phase, scoped to the judge surfaces first (JoinScreen ✓ already fine → Welcome → Dashboard → GradingScreen), admin screens later.

### 3. A new competition drops the organizer into a dead end
Create a competition → you land on an empty leaderboard with someone else's default categories, "No contestants in this slot yet.", and no hint of what to do next. The competition's own name appears nowhere on the screen (sidebar just says "Admin").

The full first-run wizard is deliberately sequenced last (roadmap #14) — this is NOT that. Cheap interim fixes:
- **Setup-status strip** at the top of an empty competition: "① Review categories → ② Add judges & panels → ③ Add contestants" — three links to existing tabs, each with a done/not-done check computed from data that already exists. Disappears once contestants exist.
- **Competition name + org in the sidebar header** (replaces the bare "Admin"), doubling as a "which competition am I in" anchor for orgs running several.
- Empty-state copy that points somewhere: "No contestants yet — import a CSV or add them in Registrations →".

### 4. Join codes should be QR codes
In-room judge onboarding today is "read this 8-character code aloud" or "let me text you a link." A QR code next to each join code (judge points camera, done) is the difference between a 10-second and a 2-minute onboarding per judge — on competition day, times 12 judges. Worth the one small dependency (`qrcode` renders to canvas, ~no transitive deps) or a ~150-line pure QR encoder.

### 5. Provisioning page has its priorities inverted
The page leads with the org-supplied-hardware flow ("Set up this device") while join codes — the common case for most competitions — sit below the fold. Swap the order, retitle the sections around the organizer's question ("How will judges score? Their own phones / devices you provide"), and show the join *link* inline instead of only behind a Copy button.

## P2 — Screen-level polish

### 6. Registrations screen
- Header is crowded: Import CSV / Promote all ready buttons visually collide with the "add manually" hint at common widths.
- "immutable · 1 records" — developer jargon plus a grammar bug. Say "1 record · payment records are never edited" or just the count.
- **No CSV template**: an organizer's first import is trial-and-error. Add a "Download template" link (a 4-line static CSV) next to Import, plus the accepted-headers hint surfaced in UI rather than only in the README.
- The two Zeffy strips permanently occupy the top of the screen for every org, including the majority who will never use Zeffy. Collapse both behind a single "Zeffy integration ▸" disclosure row, expanded only when configured.

### 7. Org dashboard
- No product header/wordmark — the page floats unanchored (ties into P0).
- Competition cards are thin: name + raw URL. Add contestant count, judge count, and a status chip (setup/live/archived) — all computable from existing data.
- Anonymous (judge) sessions see "+ New organization" and get a server rejection after filling the form (already in the ledger): hide the button for `user.isAnonymous`, show "You're joined as a judge — create an account to run competitions."

### 8. Leaderboard
- Slot tabs don't say which slots have people — add counts ("5 Ajzā' · Sisters · 3") so organizers stop clicking through empty slots.
- "0 / 4 · in progress" reads like nothing has happened even when scores are showing. Clearer: "0 of 4 judges finished".

### 9. Landing page
- Headline wraps awkwardly ("…end to\nend"); tighten the copy or set a max-width that breaks cleanly.
- No product visual — a single screenshot (leaderboard or grading) under the CTAs would do more than the three feature cards.
- "Open source — run it yourself" should link to the GitHub repo.

### 10. Feedback & dialogs
- Kick errors surface in the provisioning card's status note, far from the Kick button that was clicked (ledgered) — per-row inline errors.
- `window.confirm` for kick/rotate/remove is functional but jarring against the app's visual language; a small styled confirm becomes worth it once there are 4+ destructive actions (there are now).
- Import/error banners: give the error banner a dismiss ×, and auto-clear stale errors when a new action starts (rotateToken already ledgered).

### 11. Accessibility (real gap, cheap to fix incrementally)
- The admin sidebar nav, Sign out, ← Dashboard, and several row actions are **clickable `<div>`s** — invisible to keyboards and screen readers. Convert to `<button>`/`<a>` (styling unchanged) as files get touched.
- No visible focus states on custom buttons; add a global `:focus-visible` outline in the theme.
- Steppers (−/+) rely on color and tiny glyphs; ensure `aria-label`s ("Add prompted deduction") — judges with larger text settings are a real audience.

## P3 — Later, mostly already on the roadmap

- **i18n + RTL** (roadmap #3) — the audience makes Arabic near-mandatory; string-wrapping should ride along with the responsive pass since both touch every screen.
- **Per-org branding** (logo on projector/welcome screens) — the paid-feeling feature of this list.
- **In-app org/competition switcher** (top-left dropdown) once orgs commonly run multiple competitions.
- Native mobile apps (roadmap #2b) — only after the responsive web pass proves what's actually needed.

---

## Suggested sequencing

1. **De-brand sweep + empty-state guidance + quick polish batch** (items 1-partial, 3, 6, 7, 8, 9, 10 are all small; one phase, huge perceived-quality jump)
2. **Responsive judge pass + QR codes + provisioning reorder** (items 2, 4, 5 — one phase, makes the flagship flow match the pitch)
3. Accessibility ride-along rule: every touched file converts its clickable divs (item 11)
4. i18n/RTL next per roadmap, then the engines

Item 1's naming decision is yours; everything else is executable as written.
